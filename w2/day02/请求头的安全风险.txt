## 1. Host 头攻击 | 缓存投毒

### 1.1 Host 头攻击

**原理**
HTTP/1.1 必须携带`Host`，服务器用 Host 确定访问哪个虚拟站点。
Host 由客户端自由控制，如果后端**直接把 Host 头拼进业务逻辑**，不做白名单校验，就会触发漏洞。

**常见场景**

1. 邮件发送：业务代码 `link = f"https://{host}/reset?token=xxx"`，把 Host 拼进重置密码链接。
攻击者发请求：`Host: attacker.com`，服务器生成的重置邮件链接变成 `https://attacker.com/reset?token=xxx`。
受害者点链接，跳转到黑客网站，窃取 token。
2. 页面输出：直接把 Host 渲染到 HTML 页面，造成 XSS。
3. SSRF：后端拿 Host 去发起内部请求，攻击者篡改 Host 指向内网地址，触发 SSRF。
GET /reset HTTP/1.1
Host: attacker.com
User-Agent: curl/8.17.0

1.2 Host 头引发的 HTTP 缓存投毒（Cache Poisoning）
原理
CDN / 反向代理会缓存响应，缓存的 key 一般是「URL+Host」。
攻击者发送恶意 Host 请求，CDN 缓存了带恶意 Host 的响应。
普通用户正常访问网站（正常 Host）时，CDN 直接返回缓存的恶意页面，所有访问用户都中招。
条件
存在 CDN / 缓存代理
后端页面内容依赖 Host 头渲染
缓存没有正确把 Host 作为缓存 key 或者校验 Host
区分：Host 头攻击是单次受害者触发；缓存投毒是污染缓存，批量影响所有访问用户。
防御
后端校验 Host 白名单，不在白名单直接 403 拒绝，不要直接使用原始 Host 变量
不要把 Host 直接拼接进 URL、邮件、页面


2. XFF X-Forwarded-For → IP 伪造、白名单绕过
原理
X-Forwarded-For 设计初衷：用户 → 代理 → 后端。代理把真实客户端 IP 写到 XFF 头传给后端。
格式：X-Forwarded-For: 真实IP, 代理IP1, 代理IP2
重点：XFF 是 HTTP 请求头，完全由客户端自定义，代理默认不会校验！
漏洞场景：后端直接从 XFF 头读取 IP 做访问控制（IP 白名单、登录 IP 限制、IP 封禁），不去读取 TCP 连接真实源 IP。
GET /admin HTTP/1.1
Host: target.com
X-Forwarded-For: 127.0.0.1

# 危险！直接取header，不读socket真实IP
client_ip = request.headers.get("X-Forwarded-For")
if client_ip == "127.0.0.1":
    allow_access_admin()
攻击者直接伪造 XFF 为 127.0.0.1，绕过内网 IP 白名单，访问后台。
补充坑点：XFF 多 IP 场景
X-Forwarded-For: 1.1.1.1, 127.0.0.1
部分后端取 XFF最后一个 IP，部分取第一个，两种写法都要测试。
防御
后端优先读取 TCP 连接真实源 IP（socket 来源 IP）
只有可信代理（Nginx/CDN）才允许写入 XFF；在代理层配置固定 XFF，不接受客户端传入的 XFF


3. User-Agent → UA 注入、WAF 绕过
3.1 UA 注入
原理：后端直接把 User-Agent 原样拼入 SQL 语句、页面 HTML、日志查询、命令执行，没有过滤 / 转义。
INSERT INTO access_log (ua) VALUES ('{User-Agent}')
INSERT INTO access_log (ua) VALUES ('' or 1=1 --')

场景 2：XSS
后端把 UA 直接渲染到页面：<div>您的浏览器：{{user_agent}}</div>
UA 设置：<script>alert(1)</script>，页面直接渲染触发 XSS。
很多网站访问日志会记录 UA，日志后台如果直接渲染日志内容，就会存储型 XSS。

3.2 WAF 绕过
WAF 很多规则是基于 UA 识别爬虫 / 扫描器。
WAF 拦截 curl/python-requests 默认 UA。
攻击者修改 UA 伪装成浏览器：
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/120.0.0.0 Safari/537.36
绕过 WAF 爬虫检测。
GET /page HTTP/1.1
Host: target.com
User-Agent: <script>alert(1)</script>

防御
UA 输出到 HTML 做 HTML 转义；进入 SQL 使用预编译参数
UA 仅做日志记录，不要拿 UA 做安全鉴权

4. Referer → 伪造来源，绕过来源校验
原理
Referer 头告诉服务器：用户是从哪个页面跳转过来的。
很多业务错误认为：Referer 是可信的，用来做 CSRF 简易防护、来源白名单。
但是 Referer 完全客户端可控，可以任意伪造。
场景：简单 CSRF 防护只校验 Referer，要求来源必须是本网站。
攻击者请求带上：
Referer: https://target.com/login
服务器校验通过，成功执行敏感操作。
GET /change_pwd?new=123456 HTTP/1.1
Host: target.com
Referer: https://target.com/home

ref = request.headers.get("Referer")
if ref.startswith("https://target.com"):
    # 允许修改密码
    change_pwd()
攻击者随便伪造 Referer 直接绕过。
重点区分：Referer 不能用来防御 CSRF！CSRF 正确防御是 CSRF Token。Referer 只能作为辅助审计，不能作为安全校验。
额外用法：WAF 的来源检测绕过。WAF 拦截外部网站发起的请求，伪造合法 Referer 绕过。
防御
禁止只用 Referer 做鉴权；敏感操作使用 CSRF Token。


5. Cookie / Authorization → 会话劫持、未授权访问
5.1 Cookie 会话劫持
Cookie 是浏览器维持会话的凭证（sessionid）。
前提：网站使用 HttpOnly=False。
攻击方式：XSS 漏洞 → JS 读取 document.cookie，拿到 sessionid。
攻击者复制 Cookie，在自己浏览器带上这个 Cookie，直接登录受害者账号
GET /profile HTTP/1.1
Host: target.com
Cookie: sessionid=victim_session_token
攻击者拿到 sessionid，直接放入请求，身份就是受害者。
补充风险：
HTTP 明文传输 Cookie：中间人抓包直接窃取 Cookie。HTTPS+Secure 标记可以防止。
Cookie 没有 SameSite，容易被 CSRF 携带 Cookie。

5.2 Authorization 未授权访问 / 凭证劫持
Authorization 头用于 Basic、Bearer Token 认证。
Basic：账号密码 Base64 编码（不是加密，可直接解码）
Bearer：JWT / Token 令牌
攻击场景：
凭证泄露（日志、源码、前端），攻击者直接复制 Authorization 头，发送请求，接管账号。
未授权：后端没有校验 Authorization 头有效性，或者接口遗漏鉴权，不带凭证也能访问敏感接口。
弱 JWT：JWT 签名密钥弱，攻击者伪造 JWT，构造 Authorization: Bearer 伪造 token，越权访问。
GET /admin HTTP/1.1
Host: target.com
Authorization: Basic YWRtaW46MTIzNDU2
YWRtaW46MTIzNDU2 = admin:123456 base64 编码。
防御
Cookie：HttpOnly、Secure、SameSite；全站 HTTPS
Token：短期有效期，强签名；后端每个敏感接口强制校验 Authorization
敏感凭证禁止日志打印
